## 1. Vision

**A first-person action experience where the player fights AT cosmic scale — using galaxies, stars, and nebulae as terrain to grapple, leap from, and swing through.**

Reference touchstones (combine in this order of importance):
- **Gurren Lagann — Simon vs Anti-Spiral.** Visual signature: galaxies wielded as weapons, pure deep-space backdrop, brilliant saturated colors against black, scale of "stars are throwable."
- **Ultrakill / Echo Point Nova / Straftat.** Movement signature: fast first-person, grappling, momentum-driven traversal, no friction, parkour-feel.
- **Armored Core / Chromehounds / Gundam.** Mech signature: weighty piloted war-machines, hardware/military-industrial feel, customizable mechs, combat at scale. The humanoid/mech avatar should feel like a piloted machine, not a person.
- **SpaceEngine** (Steam) for visual *reference quality only* — we are not procedurally simulating the universe. We are handcrafting cinematic battle arenas.

**Current focus:** environment first. Get the cosmic arena feeling right before adding movement, grappling, combat.

**CONFIRMED END GOAL (2026-05-31): PvP combat arenas.** Multiplayer is the destination — but there is a TON of work first and we are explicitly NOT thinking about networking/replication yet. Build solo for now; design the environment/arena with eventual arena-combat in mind (a central landmark, clear orientation, bounded play space). Networking is a far-future phase.

## 3. Architectural Decisions

ADR entries — newest at top. Format: date · status · context · decision · consequence.

### ADR-009 · 2026-06-01 · Adopted · Gravitational lensing via in-shader ray bending (approach A), not post-process
**Context.** The flat disk didn't bend around the hole — edge-on it occluded the core and there was no Interstellar/M87 wrap. Full post-process lensing (`M_PPLensing2`) is parked (per-frame C++ `ProjectWorldToScreen`+MPC, SceneTexture Bind compile issue, invisible to SceneCapture).
**Decision.** Bend the marching ray toward the hole each step (∝ 1/r²) inside `M_RaymarchDisk` (`build_disk_lensed.py`), with `CaptureR` terminating rays that cross the shadow. Tunable `LensStrength` (default **16000**), `CaptureR` (15000). Also switched the disk march to **analytic ray-sphere bounds** (`BoundR`=OUTER·1.5) with `tNear=max(0,…)`, and enlarged the disk box to a near-cube (`spawn_rmdisk.py`, `sz` now = `sxy`) so the wrapped image isn't clipped. Full PP lensing (approach C — background-star lensing) deferred.
**Consequence.** Disk's far side arcs over the shadow; shadow always framed by light, from any free-fly angle, and renders in SceneCapture (fast iteration). Heavier (64-step march + per-step bend). Background stars/galaxies NOT yet lensed (the deferred C pass).

### ADR-008 · 2026-05-31 · Adopted · Black hole = raymarched volumetric disk + gravitational lensing (the legit RT technique)
**Context.** User wants the M87/TON618 reference look. Those reference images are OFFLINE SpaceEngine renders (volumetric raymarching + real light-bending), not real-time. We tried flat-disk shaders (smooth, no filaments) and point-cloud sprites (granular, no lensing, no volume) — both are cheap approximations that hit a ceiling. User chose: go the legit real-time path, cinematic-first (optimize later).
**Decision.** Build (A) a **raymarched volumetric accretion-disk material** (march a 3D noise density field inside a Box mesh → lush continuous turbulent gas, temperature-graded fire colors, Keplerian swirl) and (B) **gravitational lensing** (localized translucent distortion sphere around the hole, bending the background + wrapping the disk over the shadow — the iconic look; chosen over full-screen PP to avoid per-frame screen-position plumbing and work from any angle as the player flies).
**Consequence.** Shader-heavy (raymarch = many noise samples/pixel). Acceptable now per "cinematic now, optimize later"; revisit with step-count/LOD later. This supersedes the point-cloud disk and flat-disk attempts for the black hole. (Point-cloud is still the right tool for the star GALAXIES.)

### ADR-007 · 2026-05-30 · Adopted · Locked-exposure PPV makes fast captures match the viewport
**Context.** My fast SceneCapture screenshots looked deep/saturated while the user's editor viewport looked milky/washed and blew galaxies to white — because the editor used eye-adaptation (auto-exposure) + bloom that the SceneCapture bypassed. I was tuning blind.
**Decision.** Added an unbounded `PPV_DeepSpace` PostProcessVolume with **locked exposure** (`AEM_MANUAL` + min==max auto-exposure brightness) and tamed bloom (intensity 0.35). Verified by capturing the same camera via fast SceneCapture (`screenshot.py`) AND true viewport HighResShot (`screenshot_real.py`) — they're now essentially identical.
**Consequence.** `screenshot.py` (~1.3s) is trustworthy as "what the user sees." Use `screenshot_real.py` (~40s) only for occasional spot-checks. Any future exposure-look tuning happens on the PPV, not per-capture.

### ADR-006 · 2026-05-30 · Adopted · Scripts MUST save the level; avoid Live Coding for struct/UPROPERTY changes
**Context.** Editor crashed on Play (`Cast of Default__Object to Actor failed` in the PIE spawn path) and the level couldn't be restored — because no script had ever saved the level, so all today's actor state lived only in the dirty in-memory world. PIE duplicates that in-memory world; duplicating Python-spawned actors that were never serialized to disk is unstable. Suspected trigger: Live-Coding hot-patch of `AAlienCamera` (a C++ base of the `BP_Camera` Blueprint) *after adding new UPROPERTYs*.
**Decision.**
  1. Any script that mutates the level MUST call `LevelEditorSubsystem.save_current_level()` at the end. `rebuild_scene.py` is the canonical idempotent rebuild.
  2. Python-spawned mesh actors stay `MOVABLE`, never `STATIC` (static + Python spawn destabilizes PIE world duplication).
  3. When C++ changes add/remove UPROPERTYs or USTRUCT fields on a class with a Blueprint child: do a FULL editor-closed rebuild, NOT a Live Coding patch. Live Coding is fine for function-body logic only.
**Consequence.** Scene is reproducible from `rebuild_scene.py` in ~30s, and the saved `.umap` survives crashes. Slightly slower C++ iteration when touching the camera's properties.

### ADR-003 · 2026-05-30 · Adopted · SceneCapture2D for fast iteration screenshots
**Context.** `HighResShot` console command takes 30-45s in editor + silently no-ops when UE isn't focused.
**Decision.** Default screenshot path = transient `SceneCapture2D` actor → `TextureRenderTarget2D` → `RenderingLibrary.export_render_target`. Captures at editor camera POV in ~1.3s.
**Consequence.** SceneCapture bypasses the level PostProcessVolume and auto-exposure, so it shows "true" pixel values — better for tuning, but final HighResShot will look different (more tonemapped). Use HighResShot only for hero renders.

### ADR-002 · 2026-05-30 · Adopted · Bypass Enhanced Input for camera

**Decision.** `AAlienCamera::Tick` reads `PC->GetInputMouseDelta` directly, bypasses the EI pipeline entirely.
**Consequence.** Works. Code is uglier. Revisit if EI is needed elsewhere.

### ADR-001 · 2026-05-30 · Adopted · MPC-driven shader bus
**Context.** Needed a single update path for shaders that respond to time-of-day, black hole position, etc.
**Decision.** Two MPCs — `MPC_TimeOfDay` and `MPC_BlackHole` — populated with the parameters listed in §5. All materials read from these; per-frame updates flow through `BP_SceneDirector::Tick` (eventually).
**Consequence.** Materials never need per-instance parameter chaos. MPC names are load-bearing (the C++ in `SceneDirector.cpp` refers to them by string).
